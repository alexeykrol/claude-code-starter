# Claude Code Starter v6.2.0

## Summary

`v6.2.0` is about **project memory** — making it durable, layered, and analyzable. It restores two layers the framework had in v4 and lost in v5 (ARCHITECTURE, BACKLOG), introduces two new layers (INVARIANTS, methodology), and adds dialog preservation so the agent's own working sessions don't evaporate.

The driving observation comes from a user-submitted regression report: collapsing memory into a single `SNAPSHOT.md` caused the agent to repeatedly violate project invariants — eight separate `DROP TABLE` antipattern reoccurrences in one codebase — because there was no place for the contract layer to live. Memory lives on two axes; one file can't hold both.

This is the first GitHub Release of v6.2.

## What's New

### Two-axis memory model

Memory now lives on two distinct axes:

**Axis 1 — Contracts (stable, slow-changing):**
- `.claude/ARCHITECTURE.md` — restored from v4, system map
- `.claude/INVARIANTS.md` — new, hard rules whose violation is a bug
- `methodology/` — new, formal methodologies for automated pipelines

**Axis 2 — State (fast-changing, session-level):**
- `.claude/SNAPSHOT.md` — current point of work (existing)
- `.claude/BACKLOG.md` — restored from v4, Next / Soon / Later / Won't do
- `.claude/dialogs/` — new, archive of session JSONLs

Both `CLAUDE.md` templates document this model in a new "Слои памяти" section so future "let's simplify" passes can't quietly collapse it back.

### Methodology layer with maturity ladder

`methodology/_HOW-THIS-GROWS.md` documents the ladder:

```
draft     — 5-line observation (fillable in 2 minutes)
   ↓ when seen in 3+ places
pattern   — concept + anti-patterns
   ↓ when prompt skeleton stabilizes
mature    — full spec: routing signals, decomposition, prompt skeleton
   ↓ when called consistently
crystallized — part moved to deterministic code, methodology = spec
```

The low entry threshold is the design intent: better unpolished draft than lost insight. Four stage-specific templates (`draft.md`, `pattern.md`, `mature.md`, `crystallized.md`) cover the lifecycle. One canonical mature example (`00-example-llm-as-component.md`) ships as a model.

Global copy at `~/.claude/methodology/` after `install-global.sh`.

### Dialog preservation

Claude Code writes session conversations as JSONL files at `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`. These have retention; the platform eventually garbage-collects them. The framework now preserves them:

- `rules/dialog-preservation.md` — why, where, when, how, security policy per `repo_access`
- `scripts/save-dialogs.sh` — idempotent copy + `INDEX.md` maintenance; macOS bash 3 compatible
- `/save-dialog` skill — interactive entry point with optional note
- `/finish` auto-calls `save-dialogs.sh` before commit
- `.gitignore` excludes raw JSONL by default — privacy-first

### CLI / install changes

- `install_common.sh` — new helpers `install_methodology_scaffold()`, `install_memory_layers()`; `backup_existing`/`rollback` include new memory files
- `install-global.sh` 6.2.0 — installs `templates/global/rules/`, `~/.claude/methodology/`, global `/save-dialog`
- `build-release.sh` — bundles `templates/methodology/`

## Upgrade Notes

### From v6.1

The v6.2 installer detects existing v6.1 installs as `upgrade` and runs additive migration. New memory files are created only if they don't already exist. The CLAUDE.md merger (Python helper from v6.1) preserves all custom user content. No data loss expected.

If the existing project had a CLAUDE.md that already used SNAPSHOT-as-everything, the new ARCHITECTURE/BACKLOG/INVARIANTS files will be created empty (with hint comments and one example each). Migrating content from SNAPSHOT into them is a one-time manual judgment call.

### From v5.x

Same migration path. The installer runs additive migration end-to-end.

## Known Limitations

- `methodology/` cross-references use `[[link]]` wiki syntax; there is no auto-resolver yet
- `save-dialogs.sh` requires `bash` and standard POSIX tools; runs on macOS and Linux
- Dialog cleanup before public/shared push (`scripts/cleanup-dialogs.sh`) is referenced but not yet implemented — current guidance is "keep dialogs local in shared/public repos"

## Compatibility

- Backward compatible with v5.x and v6.1.x installer flags
- Existing projects can migrate by running v6.2 installer; no data loss expected
- All 11 smoke tests pass on a freshly cloned checkout
